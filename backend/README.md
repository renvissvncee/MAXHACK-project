# Backend «Приют»

Реализован полный backend MVP: FastAPI/PostgreSQL, бот MAX, авторизация mini-app, профили, предложения, запросы, контакты после мэтча, отзывы и надёжная очередь MAX-уведомлений.

## Запуск через Docker

Из корня MAXHACK-project скопируйте `.env.example` в `.env`, задайте собственный POSTGRES_PASSWORD. Для текущего шаблона строки подключения используйте пароль из букв и цифр (например, результат `openssl rand -hex 24`); специальные символы требуют URL-кодирования. Не публикуйте `.env` или вывод Compose с подставленными секретами.

```sh
cp .env.example .env
# Отредактируйте POSTGRES_PASSWORD в .env
docker compose up --build -d
```

Нужен работающий Docker Engine. Backend доступен на http://localhost:8000, документация — http://localhost:8000/docs. PostgreSQL доступен только внутри Compose; его порт не опубликован. BACKEND_PORT меняет локальный порт backend.

```sh
curl -i http://localhost:8000/api/health/live
curl -i http://localhost:8000/api/health/ready
docker compose logs backend
docker compose down
docker compose up -d
```

`live`: 200 и `{"status":"ok"}`. `ready`: 200 и `{"status":"ready"}` при успешном SELECT 1; иначе 503 и `{"status":"unavailable"}`. Проверка БД ограничена таймаутом. Проверка ready пока подтверждает только соединение, не наличие схемы приложения.

Данные PostgreSQL сохраняются в именованном томе после `down`. Не используйте `down -v`, если хотите сохранить данные. Изменение пароля в .env не меняет пароль уже инициализированной БД.

Воспроизводимая проверка отказа: `docker compose stop db`, запрос ready должен вернуть 503, live — 200; затем `docker compose start db` и повтор ready после запуска БД.

## Локальный Python

Python 3.13. Из каталога backend:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
cp .env.example .env
# Укажите DATABASE_URL доступного PostgreSQL
.venv/bin/python -m uvicorn app.main:create_app --factory --reload
.venv/bin/python -m pytest -q
```

Локальный Python требует отдельно доступной БД; Compose по умолчанию не публикует PostgreSQL наружу. Для обычной работы используйте полный Compose.

`DATABASE_URL` обязателен, имеет формат `postgresql+asyncpg://...`. `DATABASE_TIMEOUT_SECONDS` — таймаут readiness (по умолчанию 3 секунды). Файл .env ищется в рабочем каталоге. Настройки читаются при старте приложения, секрет подключения скрыт в представлении Settings.

## Устройство

`main.py`: factory и lifecycle; создаёт engine и фабрику сессий, освобождает соединения при остановке. `db.py`: отдельная сессия на запрос через Depends; будущая бизнес-операция сама задаёт границу транзакции. `api/health.py`: HTTP-контракт состояния. `config.py`: проверка окружения.

Проверка live не зависит от БД. Потеря БД не останавливает HTTP-сервер. pool_pre_ping проверяет соединения при выдаче из пула. SQL и параметры не логируются; readiness пишет только имя события без текста ошибки драйвера. Персональных данных и внешних интеграций на этом этапе нет.

`requirements.in` и `requirements-dev.in` задают прямые зависимости; соответствующие .txt фиксируют установленные версии, включая транзитивные. Docker устанавливает только runtime-зависимости.

Тест health-контракта имитирует доступность и отказ БД; он не заменяет проверку с настоящим PostgreSQL. Docker-сборка и её длительность должны быть проверены при работающем Docker Engine.

Актуальный статус и оставшаяся ручная приёмка: `../docs/implementation-plan.md` и `../docs/submission-checklist.md`.

## Этап 2 — бот MAX (локальная разработка)

Реализованы клиент API, ответы на bot_started, /start и /help, кнопка mini-app и отдельный worker бизнес-уведомлений. Контакт второй стороны выдаётся только участникам принятого запроса. Прямой формат ссылки по MAX ID ещё нужно проверить на реальных клиентах.

Из каталога backend добавьте в свой .env `MAX_BOT_TOKEN`. Для уже подключённого mini-app задайте `MAX_BOT_USERNAME` (без @) и `MAX_MINI_APP_ENABLED=true`. Не включайте кнопку до настройки приложения на платформе MAX. Пользовательские .env автоматически не изменялись.

```sh
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m app.max_bot.polling --check
.venv/bin/python -m app.max_bot.polling
```

`--check` вызывает GET /me и GET /subscriptions; не читает события и не отправляет сообщения. Активный webhook блокирует polling; подписки автоматически не удаляются. При ошибке проверяйте настройки, подключение и код HTTP в сообщении. Если TLS не доверяет сертификату MAX, настройте доверенный CA bundle через SSL_CERT_FILE; не отключайте проверку TLS.

Запускайте ровно один polling-процесс на токен. Остановка — Ctrl+C. FastAPI и бот пока запускаются независимо; бот не требует БД. Перед началом polling нужен токен, но не DATABASE_URL.

Проверка: запустите бота, откройте диалог в MAX и нажмите Старт либо отправьте /start. Ожидается приветствие. /help повторяет его; прочие сообщения, групповые чаты и сообщения ботов игнорируются. При включённой кнопке проверьте открытие подключённого mini-app на мобильном и веб-клиенте. Это нужно подтвердить реальным тестом, unit-тест проверяет только формат исходящего сообщения.

Поток: GET /updates → handlers.handle_update → client.send_message → POST /messages. Токен только в заголовке Authorization. Тексты сообщений, токены и тела ошибок MAX не логируются. Между ответами есть задержка для соблюдения лимита отправки.

Курсор marker хранится в .state/max-marker.json, обновляется атомарно после успешной обработки всей страницы. На первом запуске без marker API возвращает последнее обновление. Файл курсора относится к одному токену: при смене бота используйте другой MAX_POLLING_CURSOR_FILE.

Ограничения локального режима: при ошибке сети/API процесс завершается с ненулевым кодом, не подтверждая неуспешную страницу. Автоматического повтора отправки нет. После ручного перезапуска возможны повторные приветствия, если часть страницы уже обработана либо отправка завершилась неоднозначно. Это не exactly-once доставка; бизнес-операции и надёжные уведомления появятся с PostgreSQL. Polling не заменяет production webhook.

Официальные источники: https://dev.max.ru/docs-api/methods/GET/updates, https://dev.max.ru/docs-api/methods/POST/messages, https://dev.max.ru/docs/webapps/bridge.

TLS клиента MAX проверяется через truststore и системное хранилище доверенных сертификатов. Это позволяет использовать доверенные сертификаты macOS. В контейнере Linux хранилище отдельное: при необходимости подключите доверенный PEM bundle через SSL_CERT_FILE. Проверка TLS не отключается. reason=tls_certificate_untrusted означает проблему доверия сертификату, timeout — таймаут, connection_failed — ошибку соединения.

## Этап 3 — авторизация и профили

Проверка подписи MAX реализована по https://dev.max.ru/docs/webapps/validation: HMAC-SHA256 с ключом WebAppData, сортировка полей, сравнение подписи, проверка auth_date. Дубликаты параметров, неправильная подпись, старые данные и неверный формат пользователя отклоняются. MAX API при каждом входе не вызывается: подпись проверяется локально токеном нашего бота.

Таблицы: users (внутренний UUID, уникальный MAX ID, профиль), sessions (SHA-256 случайного токена, пользователь, срок действия). Первый вход атомарно создаёт/находит пользователя и сохраняет сессию; конфликты одновременных входов разрешаются PostgreSQL UPSERT по MAX ID. Повторный вход не перезаписывает отредактированную анкету. Сессии сохраняются после перезапуска backend, истёкшие удаляются при следующем входе.

Используем HttpOnly cookie и проверку Origin для POST/PATCH. CORS разрешает только ALLOWED_ORIGINS. Собственный API не выдаёт MAX ID и username. initData и токены не логируются; ответы ошибок валидации не содержат исходного ввода. Обычный access log показывает метод, путь и статус — не передавайте секреты в query string.

MAX_BOT_TOKEN можно оставить в backend/.env: Compose передаёт его в контейнер через env_file, файл не попадает в образ. Compose загружает корневой .env, затем backend/.env (последний имеет приоритет для токена). ALLOWED_ORIGINS и COOKIE_SECURE для Docker задавайте в корневом .env; DATABASE_URL внутри контейнера явно задаёт Compose, независимо от локального backend/.env.

```sh
docker compose up --build -d
```

Compose выполняет `alembic upgrade head` перед стартом FastAPI. Миграция 0001 добавляет users и sessions, существующие другие таблицы не затрагивает. На этом MVP предполагается один процесс запуска миграций. Внешние реплики позже потребуют отдельного migration job. Образ при самостоятельном запуске Dockerfile миграцию не выполняет — сначала запустите её явно.

Для Python из backend:

```sh
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m uvicorn app.main:create_app --factory --reload
```

Теперь используется явная application factory (`--factory`): настройки загружаются при создании приложения, до настройки CORS. Lifespan по-прежнему управляет подключением БД. Старую команду app.main:app замените новой.

Дополнительные настройки: MAX_BOT_TOKEN; INIT_DATA_MAX_AGE_SECONDS=3600; SESSION_TTL_SECONDS=86400; COOKIE_SECURE=true по умолчанию (локальный Compose false); ALLOWED_ORIGINS — JSON-массив точных origin. Для HTTPS включите Secure и укажите реальный адрес mini-app. Токен необязателен для health, но без него POST /api/auth/max возвращает 503 auth_not_configured.

Контракт и задачи frontend: `../docs/frontend-api.md`. Нет endpoints для чужих профилей, предложений или отзывов, загрузки фото и выдачи контактов. Валидация входа не подтверждает паспортную личность. initData допустимо повторно использовать в пределах срока действия; хранить и передавать его нужно как секрет. Нет общего rate limiter — перед публичным запуском потребуется ограничить частоту входа на reverse proxy.

Unit-тесты: `.venv/bin/python -m pytest -q`. Сквозной тест PostgreSQL запускается только с TEST_DATABASE_URL на выделенной БД с именем, заканчивающимся на _test. Он применяет миграции, создаёт синтетических пользователей и сохраняет тестовые данные; не направляйте его на рабочую БД. Проверяет вход, профиль, повторный вход, изоляцию пользователей, выход, истечение сессии и сохранность после перезапуска приложения.


## Этап 4 — предложение хозяина и поиск

В миграции 0002 появилась таблица `listings`, привязанная к владельцу уникальным ограничением. PUT `/api/me/listing` создаёт или обновляет одно предложение через PostgreSQL UPSERT: повтор отправки/одновременные сохранения не создают второе предложение. GET `/api/me/listing` возвращает текущее предложение или null. Создание разрешено заполненным профилям (город + интересы). Удаление/снятие с публикации пока не поддерживается согласно MVP-решению, что карточка остаётся открытой для новых обращений.

GET `/api/listings` ищет только предложения других пользователей по точному городу без учёта регистра, вместимости и доступности. `date_from` и `date_to` должны присутствовать вместе; предложение должно покрывать поездку целиком, граничные дни включены. Пагинация через limit/offset. GET `/api/listings/{id}` также скрывает своё предложение. Ни API, ни схема не блокируют пересекающиеся запросы; это будет отдельный этап запросов/матчей.

Фото предложений пока возвращаются как `photos: []`, но рейтинг и счётчик считаются по реальным отзывам. Контракт mini-app: `../docs/frontend-api.md`; спецификации: `../docs/openapi.json` и `../DATA-API.yaml`.

Миграция 0002 и сценарий создания/изменения/поиска проверены на выделенном временном PostgreSQL. Полный список тестов: `.venv/bin/python -m pytest -q`; PostgreSQL тесты запускаются с `TEST_DATABASE_URL` на отдельной БД с суффиксом `_test`.

## Этап 5 — запросы и согласие на общение

Миграция 0003 добавляет stay_requests. API `/api/requests` реализует создание с clientRequestId, списки входящих/исходящих, решение хозяина и закрытый endpoint контакта. Сервис `app/services/requests.py` управляет транзакциями; блокировки PostgreSQL защищают повторную отправку и конкурирующие решения. Финальные решения не меняются. Контакт виден только участникам принятого запроса, без генерации неподтверждённых ID-ссылок.

Применение: `docker compose up --build -d backend` (или из backend `.venv/bin/python -m alembic upgrade head`). Миграция создаёт новую таблицу, существующие профили и предложения не меняет. Тест `tests/test_requests_postgres.py` проверяет права, дубли, конфликты, матчи, контакты и перезапуск на отдельной TEST_DATABASE_URL. HTTP-контракт: `../docs/frontend-api.md`. UI запросов, отзывы, уведомления и доставка контактов через бота пока отсутствуют.

## Этап 6а — отзывы и репутация

Миграция 0004 добавляет reviews с уникальной парой author_id/subject_id. `app/services/reviews.py` проверяет наличие accepted-запроса между участниками, сохраняет отзыв PostgreSQL UPSERT и рассчитывает репутацию. Оценки 1–5, текст до 2000 символов; отзыв доступен сразу после матча. Повторные матчи не увеличивают вес автора. API `/api/users/{id}/review` и `/api/users/{id}/reviews` описан в frontend-api.md. Рейтинг предложений теперь берётся из отзывов о хозяине. UI отзывов, модерация, удаление и уведомления пока не реализованы.

Полный локальный запуск: `docker compose -f compose.yaml -f compose.full.yaml up --build -d`. Перед запуском остановите ручной polling. Подробности портов, HTTPS, cookies и остановки: [local-integration.md](../docs/local-integration.md).

Для Docker сертификаты macOS автоматически недоступны. Полный Compose поддерживает `MAX_CA_FILE` в корневом `.env` и read-only mount `.certs` → `/run/max-certs`. Инструкция экспорта уже установленных CA и проверки `--check`: [TLS в Docker](../docs/local-integration.md#tls-бота-в-docker-на-macos). Проверка TLS остаётся включённой.

## Этап 6б — лента уведомлений и MAX delivery worker

Миграция 0005 добавляет notifications: одновременно inbox приложения и очередь исходящих уведомлений. `services/notifications.py` сохраняет событие без отдельного commit; requests/reviews включают его в собственную транзакцию. Отдельный `workers/notifications.py` обрабатывает доставку с lease, повторными попытками и защищённым завершением. `GET /api/notifications`, `GET /api/notifications/{id}` и `POST /api/notifications/{id}/read` доступны только получателю.

Настройки, ограничения, включение доставки, диагностика и повтор failed-событий: [local-integration.md](../docs/local-integration.md#очередь-уведомлений). В production отправка включена; в `.env.example` она остаётся безопасно выключенной. Повторы HTTP-события не дублируют запись; неопределённый результат внешней отправки может привести к дублю сообщения MAX.

Полная проверка без сайта: из корня `python3 scripts/check_backend.py`. Создаётся отдельная тестовая PostgreSQL; MAX имитируется, рабочие данные не затрагиваются.

Опциональный туннель с прежним адресом можно включить третьим файлом: `docker compose -f compose.yaml -f compose.full.yaml -f compose.tunnel.yaml up --build -d`. Он работает в Docker и перезапускается после завершения; ошибку/занятость имени показывает в logs tunnel. Промежуточную страницу LocalTunnel эта настройка не отключает. Подробности в local-integration.md.
