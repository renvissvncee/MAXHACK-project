# Контракт mini-app — авторизация и свой профиль

Версия этапа: 0.1. Приложение использует реальную проверку подписи MAX. Обхода авторизации для demo нет. Автотесты подписывают синтетические данные отдельным тестовым ключом.

## Подключение

Frontend загружает MAX Bridge, получает `window.WebApp.initData` как исходную строку и передаёт backend без дополнительного URL-декодирования или JSON-разбора. Не используйте initDataUnsafe как доказательство личности. Не сохраняйте initData в localStorage и не выводите в логи.

Рекомендуется один origin для frontend и `/api`: локально Vite proxy `/api` → `http://127.0.0.1:8000`, на сервере reverse proxy. ALLOWED_ORIGINS backend должен содержать точный origin frontend (например, `http://localhost:5173` или `https://app.example.org`, без завершающего слеша). Браузер сам устанавливает Origin для изменяющего запроса. Нельзя подставлять Origin вручную из JS.

При прямом обращении к другому порту используйте `credentials: "include"`. Для same-origin тоже можно всегда указывать include. Не смешивайте localhost и 127.0.0.1: это разные хосты. Произвольное размещение frontend и API на разных origin не поддерживается. Для MAX Web production-cookie использует `SameSite=None; Secure`; frontend и API должны оставаться на одном HTTPS origin.

```ts
const response = await fetch('/api/auth/max', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ initData: window.WebApp.initData }),
});
const body = await response.json();
if (!response.ok) throw new Error(body.error.message);
```

Backend выставляет HttpOnly cookie `priut_session`, path `/api`. На HTTPS используются `SameSite=None; Secure` для iframe MAX Web; в локальном HTTP — `SameSite=Lax` и `COOKIE_SECURE=false`. JS не читает токен. Сессия по умолчанию действует 24 часа; данные запуска MAX принимаются в течение часа. Это идентификация аккаунта MAX, не государственная верификация личности.

## Общий ответ профиля

```json
{
  "id": "de305d54-75b4-431b-adb2-eb6b9e546014",
  "name": "Анна",
  "city": "Казань",
  "bio": "Люблю путешествия",
  "interests": ["Музыка"],
  "avatarEmoji": "👤",
  "avatarColor": "violet",
  "photoUrl": null,
  "createdAt": "2026-09-26T12:00:00Z",
  "profileCompleted": true
}
```

Пример синтетический. id — внутренний UUID, строка. MAX ID и username не выдаются. Поля verified нет: убрать демонстрационный бейдж и фильтрацию по верификации. photoUrl берётся из подписанных данных MAX; пока нет загрузки своего фото. avatarEmoji/avatarColor сохранены для совместимости текущих компонентов. profileCompleted вычисляется по непустым имени, городу и интересам; это готовность анкеты, не проверка личности.

## Маршруты

| Метод и путь | Кто и зачем вызывает | Request | Успех и изменение состояния | Ошибки |
|---|---|---|---|---|
| POST /api/auth/max | Mini-app при первом запуске/истечении сессии | JSON `{"initData":"..."}`, Origin | 200, профиль + cookie. Создаёт пользователя при первом входе; повторный обновляет только сведения MAX и выдаёт новую сессию. Предыдущая cookie текущего браузера отзывается, сессии других устройств остаются | 401 invalid_init_data; 403 origin_not_allowed; 422 validation_error; 503 auth_not_configured/database_unavailable |
| GET /api/me | Mini-app при восстановлении текущего пользователя | Cookie | 200, профиль, без изменений | 401 unauthorized; 503 database_unavailable |
| PATCH /api/me | Onboarding и редактирование профиля | Cookie, Origin, JSON с изменяемыми полями | 200, сохранённый профиль | 401 unauthorized; 403 origin_not_allowed; 422 validation_error; 503 database_unavailable |
| POST /api/auth/logout | Кнопка выхода | Cookie, Origin; тело не требуется | 204, cookie удалена, сессия отозвана. Повтор без cookie тоже 204 | 403 origin_not_allowed; 503 database_unavailable |

PATCH принимает минимум одно поле: name (1–120), city (1–120), bio (до 2000), interests (до 20 строк по 1–50), avatarEmoji (1–32), avatarColor (1–32, буквы/цифры/_/-). Строки очищаются от пробелов по краям; повторы интересов удаляются. Пропущенное поле не меняется; null не допускается. Bio можно очистить пустой строкой, interests — пустым массивом. Нельзя передавать id, MAX ID, verified, photoUrl, createdAt или profileCompleted. Чужой профиль этим API редактировать невозможно: пользователь берётся из сессии.

Единый формат ошибок для этих маршрутов:

```json
{"error":{"code":"unauthorized","message":"Сессия истекла. Войдите через MAX."}}
```

Разветвляйте UI по error.code, текст показывайте пользователю. 401 → предложить открыть mini-app заново или повторить вход со свежим initData. Не создавать бесконечный цикл повторов со старыми данными. При ошибке PATCH сохраняйте черновик. 503 не означает, что нужно сбросить форму. Ошибки валидации пока общие, без детального списка полей; те же ограничения реализуйте в форме.

6. Добавить loading/error/finally к вызовам UserContext, onboarding и формы редактирования.

Вне MAX реального initData нет. Для разработки интерфейса допустим явно выделенный frontend mock; backend не принимает произвольный user_id и не имеет demo-login. Каталог и запросы frontend пока остаются mock — их API будет добавлен следующими этапами.

OpenAPI: `/openapi.json`, Swagger: `/docs`; сохранённая спецификация этого этапа — `docs/openapi.json`.


## Этап предложений хозяев и поиска

Все маршруты требуют серверную cookie из `POST /api/auth/max`. Изменение предложения также требует допустимый `Origin` и `credentials: "include"`.

| Метод и путь | Назначение | Успех |
|---|---|---|
| `GET /api/me/listing` | Получить моё предложение | `200 {"listing": null}` или объект предложения |
| `PUT /api/me/listing` | Создать/заменить одно предложение текущего пользователя | `200 Listing` |
| `GET /api/listings` | Поиск чужих предложений | `200 Listing[]`, по умолчанию до 50 результатов |
| `GET /api/listings/{uuid}` | Открыть чужое предложение | `200 Listing`, своё скрыто как `404` |

Тело PUT (camelCase):

```json
{
  "city": "Казань",
  "title": "Комната у Кремля",
  "shortDescription": "Тихая гостевая комната",
  "description": "Описание предложения",
  "guests": 2,
  "accommodationType": "room",
  "availableFrom": "2030-08-01",
  "availableTo": "2030-08-15",
  "tags": ["центр"],
  "amenities": ["Wi-Fi"],
  "rules": ["Не курить"]
}
```

Город и даты относятся к самому предложению. На поездку хозяина уже есть город в профиле — он может отличаться от города, где хозяин принимает гостей. Даты начала и конца включительны. Поиск требует либо обе даты, либо ни одной. Если указаны обе, интервал предложения должен целиком покрывать запрошенную поездку. Город сравнивается без учёта регистра; вместимость должна быть не меньше числа гостей. Хозяин не видит собственное предложение в публичном поиске.

Списки `tags` (до 12 элементов), `amenities` и `rules` (до 20 каждый); строки до 80 символов; повторяющиеся строки удаляются. `guests`: 1–8; `accommodationType`: `room | apartment | house | sofa`. Даты ISO `YYYY-MM-DD`, конец не раньше начала. Поля валидации вне ограничений дают единый `422 validation_error`. Незавершённый профиль даёт `409 profile_incomplete`; сначала у пользователя должны быть город и интересы. Свой список нельзя удалить или выключить в этом этапе.

Ответ `Listing` включает `id`, `host` с публичным профилем, поля предложения и доступности, `rating: null`, `reviewsCount: 0`, `photos: []`. Неподдержанные отзывы и фотографии не замокированы. Проверенного статуса нет: уберите `verified` из UI и не показывайте фиктивный значок. Предложения `frontend/src/data/listings.ts` остаются синтетическими моками и не импортируются в backend.

Фильтры: `city`, `date_from`, `date_to`, `guests`, `limit` (1–100, по умолчанию 50), `offset` (от 0). Неполный/обратный интервал даёт `422 invalid_date_range`. Запись и поиск требуют сессию; чужое/своё скрытое предложение даёт `404 listing_not_found`.

Изменения интерфейса: форму хозяина связать с `GET/PUT /api/me/listing`; каталог — `GET /api/listings` с query дат поездки и числа гостей; экран деталей — `GET /api/listings/{id}`. Старый фильтр подтверждения удалить. Моковые отзывы/рейтинги/фото не считать реальными. Backend не блокирует даты после контакта; предложение остаётся опубликованным.

## Этап 5: запросы на общение и матч

Авторизация — та же cookie. POST/PATCH требуют разрешённый Origin. Отправка означает согласие гостя общаться; принятие хозяином — матч. Это не бронирование и не подтверждение проживания.

| Метод | Назначение | Ответ |
|---|---|---|
| POST `/api/requests` | Гость отправляет запрос | 200 Request, включая повтор |
| GET `/api/requests?direction=incoming` | Входящие хозяина | 200 Request[] |
| GET `/api/requests?direction=outgoing` | Исходящие гостя | 200 Request[] |
| GET `/api/requests/{id}` | Детали для участника | 200 Request |
| PATCH `/api/requests/{id}` | Решение хозяина | 200 Request |
| GET `/api/requests/{id}/contact` | Контакт второго участника принятого запроса | 200 Contact |

Создание:

```json
{
  "clientRequestId": "593f27ec-937c-40e4-956f-82997bbf8234",
  "listingId": "de305d54-75b4-431b-adb2-eb6b9e546014",
  "dateFrom": "2030-08-01",
  "dateTo": "2030-08-05",
  "guests": 2,
  "message": "Хотим познакомиться перед поездкой"
}
```

Frontend генерирует UUID clientRequestId один раз для отправки. При таймауте повторяет те же данные с тем же UUID: ответ содержит прежний запрос без дубля. Изменение данных с прежним ID → 409 idempotency_conflict. Для нового намеренного запроса нужен новый ID; ограничения на число запросов и пересечение поездок не добавлены. message необязателен, до 2000 символов, guests 1–8. Обе даты обязательны, конец не раньше начала. При создании поездка должна помещаться в доступность предложения, а количество гостей — во вместимость. Несоответствие → 409 trip_not_available. Нет заполненного профиля → 409 profile_incomplete. Собственное или отсутствующее предложение → 404 listing_not_found.

Request содержит все поля создания, id, status (pending/accepted/declined), createdAt, decidedAt (null до решения), guest и host. Профили участников имеют формат HostSummary из ответа предложения — UUID, имя, город, bio, interests, avatarEmoji, avatarColor, photoUrl. Контактов в них нет. Это актуальные профили; параметры поездки сохранены в запросе и не меняются при редактировании предложения.

Списки поддерживают limit (1–100, по умолчанию 50), offset (от 0), сортировку от новых к старым. Неизвестный direction → 422. Чужой запрос скрывается как 404 request_not_found.

Решение: `{"status":"accepted"}` или `{"status":"declined"}`. Только хозяин: гость получит 403 host_only. Повтор того же решения возвращает прежний результат, включая decidedAt; смена финального решения → 409 request_already_decided. Одновременные решения сериализуются в БД. Принятие не проверяет повторно изменённое предложение, не блокирует даты и не изменяет его публикацию.

Контакт: `{"userId":"UUID собеседника","maxUserId":"123456789","username":null}`. MAX ID передаётся строкой во избежание потери точности в JavaScript. Username может отсутствовать. До принятия/после отклонения → 403 match_required; постороннему → 404. ID-ссылка намеренно не генерируется: её формат и открытие на реальных клиентах ещё не подтверждены. Эти данные нельзя включать в общедоступные карточки или логи.

Отдельной таблицы matches нет: принятый запрос уже хранит обе стороны и время матча. Frontend подключён к отправке, спискам, решениям и выдаче контакта. Отзывы и уведомления в backend реализованы, их frontend-экраны — следующий этап.

## Этап 6а — отзывы об общении

Один редактируемый отзыв от автора о человеке, независимо от количества матчей. Любой участник принятого запроса может оценить собеседника сразу после матча: завершение поездки не требуется и проживание не подтверждается. Это репутация человека, а не оценка конкретного жилья.

| Метод | Назначение | Ответ |
|---|---|---|
| PUT `/api/users/{userId}/review` | Создать или заменить свой отзыв о человеке | 200 Review |
| GET `/api/users/{userId}/review` | Загрузить свой отзыв для формы редактирования | 200 Review или null |
| GET `/api/users/{userId}/reviews?limit=20&offset=0` | Прочитать отзывы и общую репутацию | 200 ReviewPage |

Все endpoints требуют сессию. PUT дополнительно требует Origin из ALLOWED_ORIGINS. Тело: `{"rating":5,"text":"Было приятно общаться"}`. rating — целое число 1–5, text необязателен, максимум 2000 символов, пробелы по краям удаляются. PUT заменяет отзыв полностью: отсутствие text очищает текст. Повторная отправка не увеличивает число отзывов; при одновременных редактированиях сохраняется последний завершившийся UPSERT. id и createdAt сохраняются, updatedAt обновляется при каждом сохранении.

Review: id, subjectId, rating, text, createdAt, updatedAt, author (HostSummary без MAX ID/username). Request ID и детали поездки не публикуются. Отзывы видны всем авторизованным пользователям. Редактировать можно только свой отзыв; author определяется сессией. Удаление и модерация в этой итерации не реализованы.

Ошибки: 401 unauthorized; 403 origin_not_allowed или match_required (нет принятого запроса между этими людьми); 404 user_not_found; 422 self_review при отзыве о себе, validation_error при некорректном теле/пагинации; 503 database_unavailable. Pending и declined не дают права писать отзыв.

ReviewPage: `{"rating":4.5,"reviewsCount":2,"items":[...]}`. Средняя оценка округляется до одного знака, учитывает все актуальные отзывы о человеке, а не только страницу. Нет отзывов → rating:null, reviewsCount:0. Сортировка — createdAt по убыванию, затем id; limit 1–100, offset >= 0. Редактирование не поднимает отзыв в начало списка. Общий рейтинг и страница читаются в одном SQL snapshot.

Поля rating/reviewsCount в ответах предложений теперь содержат репутацию хозяина из БД. Имена полей не изменились. Фотографии по-прежнему не загружаются. Экраны отзывов и отображение репутации гостя во frontend остаются задачей отдельной интеграции.

## Этап 6б — уведомления и доставка MAX

Уведомление создаётся атомарно вместе с событием. Получатели: новый запрос → хозяин; принятие/отклонение → гость; первый отзыв → человек, о котором написали. Повтор запроса/решения и редактирование отзыва не создают дополнительных уведомлений. Старые события, произошедшие до миграции 0005, автоматически не импортируются. При редактировании старого отзыва уведомление также не создаётся.

| Метод | Кто/зачем | Ответ |
|---|---|---|
| GET `/api/notifications` | Текущий пользователь читает свою ленту | 200 NotificationPage |
| GET `/api/notifications/{id}` | Получатель открывает одно уведомление, включая переход из MAX | 200 Notification |
| POST `/api/notifications/{id}/read` | Получатель отмечает прочитанным | 200 Notification |

NotificationPage: `{"unreadCount":2,"items":[...]}`. Параметры: unread_only (boolean, default false), limit (1–100, default 20), offset (>=0). Сортировка createdAt DESC, затем id. unreadCount — общее число непрочитанных, не размер страницы. Лента и счётчик читаются двумя запросами: при новом событии между ними допускается кратковременное расхождение; следующий refresh его устраняет.

Notification:

```json
{
  "id": "c1b2f990-ec8b-4e5a-8641-45a07f76445c",
  "kind": "request_accepted",
  "text": "Ваш запрос в Приюте принят. Контакт собеседника доступен в приложении.",
  "targetType": "request",
  "targetId": "de305d54-75b4-431b-adb2-eb6b9e546014",
  "createdAt": "2026-09-27T12:00:00Z",
  "readAt": null
}
```

kind: request_created, request_accepted, request_declined, review_created. targetType=request ведёт к GET /api/requests/{targetId}; targetType=user_reviews ведёт к GET /api/users/{targetId}/reviews. Notification не содержит контактов, текста чужой заявки/отзыва, токенов и служебных ошибок доставки.

Все маршруты требуют cookie. POST дополнительно проверяет Origin; тела нет. Повторная отметка прочтения возвращает прежний readAt. GET сам по себе ничего не отмечает. Чужой/отсутствующий id → 404 notification_not_found; нет сессии → 401; неверный Origin → 403; неверная пагинация/UUID → 422; ошибка БД → 503.

### Frontend (реализовано)

1. Добавить экран списка уведомлений и счётчик. Загружать при открытии экрана/возврате фокуса; допустимо опрашивать раз в 30–60 секунд только пока приложение активно. WebSocket/SSE пока нет.
2. При открытии уведомления загрузить его цель и явно отправить POST /read. При ошибке сохранить возможность повторить.
3. Кнопка MAX использует `startapp=notification_<UUID>`. После успешного входа прочитать start_param через MAX Bridge, проверить формат и получить уведомление по ID; затем открыть targetType/targetId. Этот параметр не доказывает право доступа: backend проверяет получателя. Невалидный параметр/404 → обычный экран уведомлений с сообщением, без бесконечных повторов.
4. Доставка в MAX и readAt независимы. Отправленное сообщение не означает, что пользователь прочитал уведомление. Ошибка MAX не скрывает событие из ленты.
5. `start_param` используется только как маршрут: frontend принимает только `notification_<UUID>`, загружает уведомление через защищённый API и только после этого открывает цель.

### Доставка

Worker отдельно читает сохранённую очередь PostgreSQL и отправляет `POST /messages?user_id=...`. Реальная доставка выключена по умолчанию (`NOTIFICATION_DELIVERY_ENABLED=false`), лента при этом работает. Успех подтверждается корректным message.body.mid в ответе MAX. Таймаут оставляет неопределённость: MAX мог принять сообщение, поэтому повторная доставка иногда создаст дубликат. Гарантии exactly-once внешней отправки нет.

Основание: https://dev.max.ru/docs-api/methods/POST/messages — отправка по user_id и ограничение 2 сообщения/сек в один диалог. Worker отправляет не чаще одного сообщения за 1.1 секунды; 429 повторяется с задержкой. Polling приветствий остаётся отдельным процессом, общий лимит MAX для обоих потоков соблюдается через обработку 429, общей распределённой квоты пока нет.
