# План backend

Архитектура: один FastAPI backend, PostgreSQL, отдельные модули HTTP API, бизнес-логики и клиента MAX. Frontend разрабатывает другой участник. Корневой README неизменяем.

1. Каркас, настройки, PostgreSQL, Docker, live/ready и тест отказа БД.
2. MAX: локальный polling, открытие mini-app и проверка ID-ссылок на двух аккаунтах в мобильном и веб-клиенте. Для mini-app нужен публичный HTTPS-адрес.
3. Контракт frontend, авторизация по проверенному initData, профили, модели и миграции Alembic.
4. Создание одного предложения на владельца, редактирование и поиск по городу, датам и вместимости.
5. Входящие/исходящие запросы, принятие и отклонение, выдача контактов только участникам матча.
6. Отзывы после матча, расчёт репутации, сохраняемые в БД уведомления и повторная доставка.
7. Проверка всего сценария в MAX, HTTPS/webhook на сервере, demo-данные, OpenAPI, DATA-API.yaml и пакет сдачи.

Каждый этап включает тесты критических правил и актуализацию документации. Существенные спорные решения согласуются до реализации.

## Правила продукта

Один профиль совмещает гостя и хозяина. Одно предложение и один интервал доступности. Предварительное одобрение запроса может открыть контакты, но не резервирует даты и не закрывает предложение. Переписка проходит в личном чате MAX и недоступна backend. Отзыв после взаимодействия не подтверждает фактическое проживание. Username не обязателен; точный формат ID-ссылки пока не проверен. Основная метрика MVP — доля отправленных запросов, получивших предварительное одобрение хозяина: число предварительно одобренных запросов ÷ все отправленные запросы × 100%. Собственный baseline пока отсутствует; 20% — целевая гипотеза MVP, а не рыночный норматив. Предварительное одобрение не означает фактического приезда или проживания.

## Frontend

Нужны MAX Bridge и авторизация; профиль без фиктивной верификации; форма своего предложения; даты в поиске и запросе; входящие/исходящие запросы; решения хозяина; контакты после матча; отзывы о взаимодействии. Точные JSON-схемы согласуются до подключения API. Не строить ID-ссылки до проверки на реальных клиентах.

## Открытые решения

Формат ID-ссылки,  загрузка фотографий, механизм сессии и защита изменяющих запросов, доступ жюри. Оформление обязательной технической информации в README для сдачи требует отдельного согласования.

## Текущее состояние

Этап 1: каркас и health-контракт реализованы, Docker и реальный PostgreSQL проверены.
Этап 2: polling и клиент MAX реализованы и развёрнуты; токен, TLS, GET /me, /subscriptions и открытие mini-app проверены. Формат ID-ссылки ещё не подтверждён.
Этап 3: подпись initData, серверные сессии, модели users/sessions, миграция 0001 и API своего профиля реализованы.
Этап 4: предложения и поиск реализованы и проверены. Frontend подключён к Bridge, API профиля, каталогу и форме своего предложения. Вход MAX и cookie в MAX Web проверены на HTTPS deployment.
Этап 5: backend и frontend заявок подключены: форма с датами, гостями и сообщением, идемпотентная отправка, входящие/исходящие, принятие/отклонение и закрытая выдача MAX-контакта. Формат ID-ссылки остаётся неподтверждённым.

Этап 6а: один редактируемый отзыв о человеке после матча, API чтения/сохранения, репутация и frontend реализованы. Отзыв можно оставить/изменить из принятой заявки; публичный список отзывов доступен из карточки хозяина.

Этап 6б: сохраняемые уведомления, лента/read API, frontend-экран, счётчик и маршрутизация `startapp=notification_<UUID>` реализованы. Отдельный MAX worker с lease/retry готов и включён в production; перед включением пустая очередь, DB и MAX API проверены без отправки.

Этап 7 (автоматизируемая часть): подготовлены демо-данные для двух реальных MAX-аккаунтов, воспроизводимые `docs/openapi.json` и `DATA-API.yaml`, а также чек-лист сдачи. Автозагрузка фиктивных MAX-пользователей сознательно не делается: она не позволит проверить доставку и реальный контакт.

Осталось: ручной сквозной тест на двух MAX-аккаунтах, проверка формата прямой ID-ссылки и UX-доработки по результатам наблюдаемых тестов. Загрузка своих фото остаётся отдельным product decision; MVP использует аватар MAX.
