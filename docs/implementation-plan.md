# План backend

Архитектура: один FastAPI backend, PostgreSQL, отдельные модули HTTP API, бизнес-логики и клиента MAX. Frontend разрабатывает другой участник. Корневой README неизменяем.

1. Каркас, настройки, PostgreSQL, Docker, live/ready и тест отказа БД.
2. MAX: локальный polling, открытие mini-app и проверка ID-ссылок на двух аккаунтах в мобильном и веб-клиенте. Для mini-app нужен публичный HTTPS-адрес.
3. Контракт frontend, авторизация по проверенному initData, профили, модели и миграции Alembic.
4. Создание одного предложения на владельца, редактирование и поиск по городу, датам и вместимости.
5. Входящие/исходящие запросы, принятие и отклонение, выдача контактов только участникам матча.
6. Отзывы после матча, расчёт репутации, сохраняемые в БД уведомления и повторная доставка.
7. Проверка всего сценария в MAX, HTTPS/webhook на сервере, demo-данные, OpenAPI, DATA-API.yaml и пакет сдачи.

Каждый этап включает тесты критических правил и актуализацию документации. Существенные спорные решения согласуются до реализации.

## Правила продукта

Один профиль совмещает гостя и хозяина. Одно предложение и один интервал доступности. Принятие запроса открывает контакты, не резервирует даты и не закрывает предложение. Переписка проходит в личном чате MAX и недоступна backend. Отзыв после матча не подтверждает проживание. Username не обязателен; точный формат ID-ссылки пока не проверен. Метрика наблюдаемого результата MVP — матч; фактическая договорённость неизвестна.

## Frontend

Нужны MAX Bridge и авторизация; профиль без фиктивной верификации; форма своего предложения; даты в поиске и запросе; входящие/исходящие запросы; решения хозяина; контакты после матча; отзывы о взаимодействии. Точные JSON-схемы согласуются до подключения API. Не строить ID-ссылки до проверки на реальных клиентах.

## Открытые решения

Формат ID-ссылки,  загрузка фотографий, механизм сессии и защита изменяющих запросов, доступ жюри. Оформление обязательной технической информации в README для сдачи требует отдельного согласования.

## Текущее состояние

Этап 1: каркас и health-контракт реализованы, Docker и реальный PostgreSQL проверены.
Этап 2: локальный polling и клиент MAX реализованы; проверка токена через GET /me и /subscriptions прошла. Открытие mini-app и ID-ссылки требуют ручной проверки в MAX.
Этап 3: подпись initData, серверные сессии, модели users/sessions, миграция 0001 и API своего профиля реализованы.
Этап 4: предложения и поиск реализованы и проверены на отдельном PostgreSQL. Frontend подключён к Bridge, API профиля, каталогу и форме своего предложения; реальный вход MAX и cookies требуют проверки после привязки HTTPS URL.
Этап 5: запросы, идемпотентная отправка, принятие/отклонение, списки участников и закрытая выдача контактов реализованы. Повтор по clientRequestId возвращает прежний запрос; новый ID допускает новое обращение. Формат ID-ссылки остаётся неподтверждённым.

Этап 6а: один редактируемый отзыв о человеке от автора после матча, API чтения/сохранения и репутация в предложениях реализованы. Повторные матчи не добавляют вес оценке.

Этап 6б: сохраняемые уведомления, лента/read API и отдельный MAX worker с lease/retry реализованы. Реальная отправка выключена по умолчанию; проверка доставки выполнена на имитации MAX.

Следующий этап — проверка всего пути на двух аккаунтах MAX, постоянный HTTPS deployment и подготовка пакета сдачи по требованиям организаторов. Работоспособность MAX-клиентов и реальная доставка ещё не подтверждены. Открытие и вход на двух аккаунтах MAX проверяются отдельно после привязки адреса.
