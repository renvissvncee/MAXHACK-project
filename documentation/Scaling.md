# Масштабирование

## 1. Что масштабируем

В основе сервиса находится единый сценарий взаимодействия:

**Путешественник → поиск → профиль → запрос → одобрение → общение → взаимодействие → отзыв**

Продуктовое ядро включает:

- профили путешественников и хозяев;
- поиск по городам и датам;
- просмотр информации о пользователях;
- запросы на гостеприимство;
- коммуникацию;
- отзывы и формирование репутации.

Данный сценарий не зависит от конкретного города и может переноситься между различными направлениями.

Однако при масштабировании меняется не только количество пользователей.

Главная задача — создавать локальные сообщества, в которых путешественники и хозяева смогут находить друг друга.

---

# 2. Что меняется при запуске нового города

При запуске нового города не требуется создавать новый продукт.

Изменяется локальный слой сети:

- количество и активность хозяев;
- количество путешественников;
- локальные сообщества;
- каналы привлечения;
- особенности конкретного города;
- локальная модерация и поддержка.

Таким образом:

> **Продуктовое ядро остаётся единым, а в каждом городе формируется собственная локальная сеть участников.**

---

# 3. Модель роста

Первый этап:

**Москва ↔ Казань**

↓

Проверка основного сценария:

- находят ли пользователи друг друга;
- отправляют ли запросы;
- получают ли предварительное согласие;
- возникает ли реальное взаимодействие.

↓

Следующие направления:

**Москва ↔ Санкт-Петербург**

**Москва ↔ Нижний Новгород**

↓

Расширение на другие крупные города России.

---

При выборе следующего города учитываются:

- количество потенциальных путешественников;
- наличие потенциальных хозяев;
- активность локальных сообществ;
- туристическая привлекательность города;
- доступность каналов привлечения;
- результаты предыдущих запусков.

---

# 4. Главный принцип масштабирования

Мы не пытаемся сразу запускать сервис во всех городах России.

Для двухстороннего рынка важнее качество локальной сети, чем общий размер аудитории.

Наш подход:

**одна городская пара → формирование сообщества → проверка метрик → анализ → следующий город**

Это позволяет понять:

- воспроизводится ли сценарий;
- какие факторы влияют на успешность;
- какие элементы требуют адаптации.

---

# 5. Основной вызов масштабирования

Главное ограничение проекта — не техническое масштабирование.

Главный вызов:

> **создание баланса между двумя сторонами рынка.**

Для работы сервиса одновременно нужны:

**путешественники ←→ хозяева**

---

Если есть только путешественники:

- пользователи не находят подходящих вариантов;
- снижается ценность сервиса.

Если есть только хозяева:

- отсутствует достаточное количество запросов;
- участники теряют мотивацию оставаться активными.

Поэтому при запуске каждого нового города необходимо развивать обе стороны одновременно.

---

# 6. Стратегия роста сети

Вместо массового привлечения пользователей сразу по всей России используется последовательное развитие локальных сообществ.

Этапы:

## Этап 1. Формирование первой сети

Москва ↔ Казань.

Цель:

создать первые успешные взаимодействия.

---

## Этап 2. Проверка воспроизводимости

Запуск новых направлений.

Цель:

понять, сохраняются ли показатели при изменении города и аудитории.

---

## Этап 3. Расширение сети

Подключение новых городов.

Цель:

увеличение количества возможных совпадений между путешественниками и хозяевами.

---

# 7. Роль Digital ID при масштабировании

Digital ID является дополнительным элементом доверия, но не является основой масштабирования.

Основные механизмы формирования доверия:

- профиль пользователя;
- отзывы;
- история взаимодействий;
- коммуникация до встречи;
- репутация внутри сообщества.

Digital ID может использоваться как дополнительный сигнал подтверждения личности.

На текущем этапе автоматическая проверка наличия Digital ID через MAX API недоступна.

Пользователь может самостоятельно предъявить подтверждение личности другому участнику через существующий механизм.

---

# 8. Что потребуется для роста

## Технологическая часть

По мере увеличения аудитории потребуются:

- развитие продукта;
- техническая поддержка;
- аналитика;
- масштабирование инфраструктуры.

---

## Развитие сети

Основной ресурс роста:

- привлечение хозяев;
- привлечение путешественников;
- развитие локальных сообществ.

---

## Операционная часть

Потребуются:

- модерация;
- обработка жалоб;
- поддержка пользователей;
- контроль качества взаимодействий.

---

## Аналитика

Необходимо отслеживать:

- конверсию между этапами сценария;
- активность пользователей;
- баланс сторон рынка;
- успешность различных городов.

---

# 9. Основные риски масштабирования

## Недостаток хозяев

Без достаточного количества хозяев путешественники не получают ценности.

---

## Недостаток путешественников

Без гостей хозяева не видят смысла участвовать.

---

## Неравномерность городов

Разные города могут иметь разную скорость формирования сети.

---

## Доверие и безопасность

Отзывы и репутация снижают неопределённость, но не исключают полностью риск взаимодействия между незнакомыми людьми.

---

## Отсутствие истории у новых пользователей

Новые участники могут не иметь отзывов и репутации.

Для этого необходимо создавать механизмы формирования доверия с первого взаимодействия.

---

# 10. Критерии готовности к масштабированию

Перед запуском нового города необходимо оценить:

## Есть ли спрос?

→ пользователи ищут варианты и отправляют запросы.

## Есть ли предложение?

→ достаточно ли хозяев готовы принимать гостей.

## Работает ли сценарий?

→ проходит ли пользователь путь от поиска до запроса.

## Есть ли успешные совпадения?

→ приводит ли взаимодействие к реальному результату.

## Воспроизводится ли результат?

→ сохраняются ли показатели на новых направлениях.

---

# Итог

Масштабирование проекта строится не вокруг создания отдельных сервисов для каждого города.

Мы переносим единое продуктовое ядро:

> **найти человека → изучить информацию → отправить запрос → получить решение → пообщаться → сформировать репутацию**

и постепенно создаём локальные сети гостеприимства в российских городах.

Главная задача масштабирования:

> **не просто увеличить количество пользователей, а создать достаточную плотность участников, при которой путешественники и хозяева начинают регулярно находить друг друга.**
